# 文档工作台智能体

用一句话完成文档的**撰写 / 修改 / 格式 / 转换 / 查看**。模型负责理解意图，工具负责精确执行，源文件全程只读。

- 界面：Streamlit（`app.py`，课程验收用）
- 接口：FastAPI（`server.py`，后续小程序复用同一套能力）
- 核心：`core/`，与界面完全解耦

---

## 1. 快速开始

环境：Python 3.10+，本项目在 `D:\Anaconda\envs\llm_course` 下开发验证。

```bash
pip install -r requirements.txt
```

启动界面（课程验收用这个）：

```bash
streamlit run app.py
# 浏览器打开 http://localhost:8501
```

启动接口（小程序后端）：

```bash
python -m uvicorn server:app --host 127.0.0.1 --port 8000
# 接口文档 http://127.0.0.1:8000/docs
```

Windows 上也可以直接双击：

- `start.bat`：启动界面（自动检查环境、清理被占用的端口、延迟打开浏览器）
- `start-api.bat`：启动接口

跑测试：

```bash
python tests/run_cases.py
# 产出 tests/test_records.xlsx 与 evidence/测试证据索引.md
```

## 3. 六类工具

| 模块 | 工具名 | 能力 |
|---|---|---|
| 查看 | `inspect_document` | 文档结构、字数段落统计、关键词查找 |
| 撰写 | `compose_document` | 按主题+大纲生成新文档（Markdown 渲染成 DOCX，含标题/列表/表格） |
| 修改 | `edit_document` | 精确文本替换、追加段落、新增章节 |
| 格式 | `format_document` | 标题居中、字体字号、行距、首行缩进、一键报告排版 |
| 转换 | `convert_document` | DOCX↔TXT/MD、DOCX→PDF（多后端探测）、MD/TXT→DOCX、**PDF→DOCX** |
| 结构 | `structure_document` | **合并多份**、**按标题拆分**、**表格转 Excel**、**两版差异对比** |

所有工具参数化，禁止硬编码文件名；失败返回明确错误码（`NOT_FOUND_IN_DOC`、`FILE_CORRUPTED`、`SAFETY_BLOCKED` 等），不伪造成功。

## 4. Agent 两种后端

| 后端 | 说明 |
|---|---|

```ini

MODEL_PROVIDER=zhipu-openai
ZHIPU_MODEL=glm-4-flash
AGENT_BACKEND=auto
```

`.env` 已在 `.gitignore` 中，不会入库。

## 5. 安全与合规

- **路径白名单**：只允许读写 `data/uploads`、`data/outputs`、`samples`，越界返回 `SAFETY_BLOCKED`
- **原文件只读**：所有操作输出为新文件，唯一命名，绝不覆盖输入
- **哈希自检**：处理前后对源文件做 SHA-256 比对，变化即报错
- **上传落盘**：文件名净化 + 时间戳去重，拒绝非白名单扩展名
- **错误如实返回**：不吞异常、不伪造成功状态

## 6. PDF → Word：为什么排版会坏，以及怎么修

### 6.1 先说结论：不是"修排版"，是"换转换方式"

上一版的做法是"用 Word 打开 PDF 再另存 DOCX"（PDF Reflow），然后事后再去修行距、列宽、页边距。
这条路走不通，原因在产物结构：Word 会把整页文字拆成**浮动文本框**（本文档实测 1256 个），
每个框锚定在一个段落上。字号、行高、页边距一变，锚点段落重排，**所有框跟着错位** ——
表现为表格整体下移、列宽被挤、下一页内容被拽上来。此时无论怎么改 `tblW`／`tblInd`／行距，
都改不动这些框，所以"事后修"注定失败。

现在的做法是**结构重建**（`core/tools/_pdfrebuild.py`）：不复制"看起来的位置"，而是从 PDF 里读出结构。

| 从 PDF 读什么 | 重建成什么 |
|---|---|
| 横线 / 竖线的坐标 → 网格 | 真正的 Word 表格（`tblLayout=fixed`，列宽按原网格比例） |
| 每一行实际存在哪些竖线 | 合并单元格（整行只有左右两条线 → 跨列合并） |
| 字符级坐标（`rawdict`） | 同一基线上的碎片按 x 归位到各自单元格，不会被"整行当一条线"吞掉 |
| 行块的纵向间距 | 段落；间距大 → 断段，间距小 → 同一段的自动换行 |
| 行块是否水平居中 | 居中对齐（标题）或左对齐（正文） |
| 页上下 70pt 内、多页重复的行 | 节属性里的页眉 / 页脚 |
| 原 PDF 的分页 | 保留分页（一页一个科目，不跨页混排） |

产物是**可编辑、可自动换行**的 Word：改字号、改页边距、加删内容，版面都会自己重排，不会再散。

### 6.2 后端顺序（`auto`）

1. **结构重建**（默认，纯 Python，跨平台）——真表格 + 真段落，排版可控
2. **Microsoft Word（PDF Reflow）**——装 Office 才可用；保真度高但产物是浮动文本框，只作兜底
3. **pdf2docx**——纯 Python，把绝对坐标写成段落缩进，复杂表格识别弱
4. **PyMuPDF 纯文本**——只保文字，最后兜底

前面失败才回落到后面，每一档失败原因都会写进返回说明，不伪造成功。
扫描件（图片型 PDF）没有文本层，全部失败时如实提示需要先 OCR，不会输出空文档。

转换提示语会写明用了哪一档、结果如何，例如：

```
已由 PDF 生成 DOCX：结构重建（7 页 → 5 个真表格、149 个段落，覆盖 2751/2805 字）
```

### 6.3 效果对照

`evidence/preview/compare_p1.png`、`compare_p2.png` 是同一份 PDF 转换前后的左右对照
（用本机 Word 把 DOCX 再导出 PDF 渲染成图，不是截图拼接）。

数值校验（转换后 Word 导出的 PDF 实测）：

| 指标 | 结果 |
|---|---|
| 页数 | 7 页，与原 PDF 一致 |
| 表格数 | 5 个，都是真正的 Word 表格 |
| 文字覆盖率 | 2751 / 2805 字（98%，差额是页眉重复行） |
| 超出版心的文字片段 | 0 |

### 6.4 仍然存在的上限

- PDF 没有语义，表格靠"有没有线"判断：**无框线表 / 三线表** 识别不出来，会退化成普通段落
- 跨页续表会被拆成两个表；嵌套表只还原外层
- 原 PDF 里"整页套一个大框"的设计（如第 2 页那段被框住的正文）不会重建外框，只保留框里的内容
- 扫描件仍需先 OCR
- `_docxrepair.py` 仅保留给 pdf2docx 兜底路径使用（那条路径才会产生绝对定位残留）

## 7. 结构操作：合并 / 拆分 / 提取表格 / 对比

第六个工具 `structure_document`，四个动作用一套入口。界面上既可以说一句话，也可以在「📎 多份文档操作」面板里勾好文件点按钮——后者更省事，因为合并和对比天生要指定多份文件。

| 动作 | 做什么 | 关键实现 |
|---|---|---|
| `merge` | 多份 DOCX 按顺序合成一份 | 逐元素 `deepcopy`，重建图片/超链接关系，补注册缺失样式 |
| `split` | 按标题层级拆成多份 | 按 body 子元素真实顺序切片 |
| `extract_tables` | 表格导出成 Excel | 一个表一个工作表，还原横向合并单元格，表头加粗并冻结 |
| `diff` | 两版文档差异报告 | `SequenceMatcher` 段落级对齐，输出新增 / 删除 / 修改 |

### 几个刻意处理过的坑

**合并不能只搬文字。** 段落里可能带图片、超链接，它们的 `rId` 属于源文档的关系表。直接 `deepcopy` 到目标文档会变成断链，Word 打开时报「无法读取的内容」。所以复制后要重建关系（`_rebase_rels`），实在迁不过来的图片会被清掉并在提示里说明，绝不留下一个打不开的文件。

**拆分不能按 `doc.paragraphs` 切。** `doc.paragraphs` 只含段落，表格被跳过了；按它的索引切片会把表格切到错误的位置。必须遍历 `body` 的子元素。

**标题层级不规范的文档要能自动回退。** 不少文档通篇只有「标题 2」，按死 `level=1` 会一份都拆不出来。此时自动改用文档里实际存在的最小标题级别，并在结果里写明「文档没有 1 级标题，已按 2 级标题拆分」——改变行为，但绝不静默。

**对比报告里的「修改」要名副其实。** 两段文字如果几乎不沾边（相似度 < 0.45），说成「修改」会误导，所以拆成一条「删除」加一条「新增」。

### 限制（如实说明）

- 合并只处理正文，页眉页脚沿用第一份文档
- 样式冲突时以第一份文档为准（同名样式不覆盖）
- 拆分依据是 Word 的标题样式（`Heading N` / `标题 N`）；纯靠手动加粗的「标题」识别不出来，可以先用格式工具设成标题样式
- 对比只比段落文本，不比较格式差异（改字体、改行距不会出现在报告里）

其中 **T23 是 PDF→Word 的排版专项校验**：现场生成一份带网格线的表格 PDF，转换后断言「产出的是真 Word 表格、表宽不超版心、文字覆盖率 ≥85%」。这条用例就是为了防止排版问题再悄悄回来。

**T24–T31 是结构操作的专项校验**（合并 / 拆分 / 表格导出 / 差异对比 + 三条失败路径）。这些用例不只断言「调用成功了」，还要验证产物本身：合并后段落数和表格数不能少于各源文档之和；拆分出来每一份都得非空且能独立打开；导出的 Excel 要有表头且单元格非空；差异报告要真的列出条目。

- `tests/test_records.xlsx`：逐条记录入参、返回码、耗时、输出文件、可打开性、源文件哈希是否变化

## 9. 后续转小程序

核心能力在 `core/` 与 `server.py`，小程序只需：

1. 把 FastAPI 部署为 **HTTPS** 服务（小程序只允许 HTTPS）
2. 在微信后台把域名加入 **request 合法域名**（需备案域名）
3. 小程序端调 `POST /api/upload`（`wx.uploadFile`）、`POST /api/task`、`GET /api/download/{name}`

服务端已支持 CORS、返回可下载 URL、中文文件名容错；`ACCESS_TOKEN` 环境变量留了可选的令牌鉴权（默认关闭，公开部署时填上即生效）。

## 10. 常见问题

**端口被占用**

```cmd
netstat -ano | findstr :8501
taskkill /F /PID <PID>
```

或换端口：`streamlit run app.py --server.port 8502`

**`streamlit` 不是内部命令**：环境没激活，用完整路径 `D:\Anaconda\envs\llm_course\python.exe -m streamlit run app.py`

**页面能打开但按钮没反应**：确认用的是真实浏览器（Chrome/Edge）而不是内置预览面板，并确认后端进程还在

**`streamlit run app.py` 报 File does not exist**：当前目录不对，先 `cd` 到项目根目录

**PDF 转 Word 后表格仍有错位**：先看提示里的方法是不是「结构重建」。如果不是（说明重建失败已回落），多半是该 PDF 没有可用网格线（无框线表 / 三线表 / 扫描件），这类只能退化成段落或需要 OCR。结构重建成功后仍错位，请把 PDF 发我，按网格线规则补。
